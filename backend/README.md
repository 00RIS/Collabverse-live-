# Academia–Industry Platform — Backend (Phase 1 + Phase 2)

**Phase 1 (Foundation):** project structure, PostgreSQL connection, User
model, authentication, RBAC, and the four role profiles.

**Phase 2 (Skill Intelligence — partial):** the Skill Catalog, a
student's own skills, Career Roles with skill requirements, and an
explainable, deterministic Career Readiness Score. The full Assessment
engine (question bank, submissions, difficulty levels, history) is
deliberately **not** in this phase yet — it's substantial enough to be
its own follow-up pass (Phase 2b) once you're happy with the catalog and
readiness scoring below.

## 2. Database schema so far

**Phase 1 tables:** `users`, `student_profiles`, `recruiter_profiles`,
`academician_profiles`, `institution_profiles`.

**Phase 2 tables:** `skills`, `skill_relations`, `student_skills`,
`career_roles`, `career_skill_requirements`.

### New relationship types introduced in Phase 2

- **Self-referential one-to-many** (`skills.parent_skill_id` → `skills.id`):
  models parent/sub-skill hierarchy (e.g. "Machine Learning" is the
  parent of "Deep Learning"). One row can have many children but only
  one parent.
- **Self-referential many-to-many** (`skill_relations` table): models
  symmetric "related skills" (e.g. React ↔ Vue) with no hierarchy. Needs
  its own link table because a skill can relate to many other skills and
  vice versa.
- **Many-to-many via association object** (`student_skills` and
  `career_skill_requirements`): a student has many skills and a skill is
  held by many students — but the relationship itself carries data
  (proficiency level, importance weight), so it can't be a bare link
  table; it needs to be a full model with its own primary key and
  columns. Contrast this with `skill_relations` above, which has no
  extra data and so *can* be a bare table.

## 3. The Career Readiness Score — how it's calculated

Implemented in `app/services/readiness.py` as a **pure function** (no
database, no FastAPI) specifically so it's unit-testable on its own —
see `tests/test_readiness.py`, which passes 5 scenarios covering a
perfect match, a heavily-weighted missing skill, proficiency capping,
gap-priority ordering, and the empty-requirements edge case.

For each required skill (required level `R`, importance weight `W`),
and the student's own level `P` (0 if never logged):

```
ratio = min(P / R, 1.0)                       # capped — exceeding one
                                                # requirement can't offset
                                                # a different missing skill
readiness_score = (Σ W·ratio / Σ W) × 100
```

Each requirement is also labeled `strong` (P ≥ R), `partial` (0 < P < R),
or `missing` (P = 0), and the "priority gaps" list sorts partial +
missing requirements by weight — the biggest, most consequential gap
first. This is deliberately a fixed, inspectable formula rather than
anything generated by a language model, per the spec's explainability
requirement (Section 5).

**Relationship type: one-to-one**, in all four cases. `users` is the
single source of truth for login (email, password hash, role, account
status). Each profile table has a `user_id` column that is a **foreign
key** (it must point at a real row in `users`) *and* has a **unique
constraint** on it (no two profile rows can point at the same user).
Foreign key + unique together is what makes a relationship one-to-one
instead of SQLAlchemy's default one-to-many.

Why split them at all instead of one `users` table with every possible
field? A recruiter has `company_name`; a student doesn't. Cramming both
into one table means most columns are NULL for most rows, and it's easy
to accidentally let a student have a `company_name`. Four focused tables
means each one only has fields that make sense for that role, and the
database itself won't let inconsistent data in.

You have **no one-to-many or many-to-many tables yet** — those show up
starting in Phase 2 (a Student has many Skills; a Skill belongs to many
Students → many-to-many) and Phase 3 (a Project has many team members →
one-to-many / many-to-many depending on how teams are modeled).

## 3. How authentication works end-to-end

1. **Register** (`POST /api/v1/auth/register`): client sends email,
   password, role, and role-specific fields. We hash the password with
   bcrypt (`hash_password`) — the plain password is never stored or
   logged. We create one `User` row and one matching profile row, in the
   same database transaction, so you never end up with a user that has
   no profile or vice versa.
2. **Login** (`POST /api/v1/auth/login`): we verify the password against
   the stored hash and, if it matches, issue two JWTs: a short-lived
   **access token** (used on every request) and a longer-lived
   **refresh token** (used only to get a new access token later).
3. **Every protected request**: the client sends
   `Authorization: Bearer <access_token>`. `get_current_user` (in
   `app/api/deps.py`) decodes and verifies the token's signature and
   expiry, pulls the user ID out of it, and loads that `User` from
   Postgres. If any step fails, the request is rejected with 401 before
   your endpoint code runs.
4. **RBAC**: `require_role(UserRole.RECRUITER)` wraps `get_current_user`
   and additionally checks the user's role. Any future endpoint that
   should only be callable by, say, recruiters or institution admins
   just adds this one dependency — no new logic needed.
5. **Refresh** (`POST /api/v1/auth/refresh`): when the access token
   expires (30 min by default), the client sends the refresh token to
   get a new access token, without the user re-entering their password.

## 4. Running it locally

You'll need PostgreSQL running (locally or via Docker) and Python 3.11+.

```bash
cd backend
python -m venv venv
source venv/bin/activate      # on Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# then edit .env: set DATABASE_URL to your real Postgres connection
# string, and SECRET_KEY to a long random value
#   python -c "import secrets; print(secrets.token_hex(32))"

# Create the initial migration and apply it
alembic revision --autogenerate -m "create users and profile tables"
alembic upgrade head

# Run the API
uvicorn app.main:app --reload
```

Then open `http://127.0.0.1:8000/docs` — FastAPI's interactive Swagger
UI, where you can try `/register`, `/login`, and `/users/me` directly in
the browser.

## 5. Try it end-to-end (after running migrations + the server)

1. Register an academician, then use their access token to `POST
   /api/v1/skills` a few skills (e.g. "Python", "SQL", "Power BI") and
   `POST /api/v1/careers` a role (e.g. "Data Analyst"), then `POST
   /api/v1/careers/{id}/requirements` to attach required proficiencies
   and weights.
2. Register a student, log in, `PUT /api/v1/students/me/skills` to add
   a couple of the skills above at various proficiency levels.
3. Call `GET /api/v1/careers/{id}/readiness` as that student — you'll
   get back the score plus the strong/partial/missing breakdown and
   ranked recommended actions.

## 6. What's deliberately NOT here yet

- Password reset flow and email verification (the spec calls these out
  as "architecture" to design — worth a dedicated pass once you decide
  on an email provider).
- Refresh token revocation / logout blacklisting (current refresh tokens
  are valid until they expire; a production version would track issued
  tokens in the DB so you can invalidate them on logout).
- Rate limiting, audit-log table, and account-lockout after failed
  logins (Section 32, Security).
- **Assessments** (Section 4): question bank, difficulty levels,
  submissions, and assessment history. This is the natural "Phase 2b" —
  once built, a passed assessment would upgrade a `StudentSkill.source`
  from `self_declared` to `assessment_verified`, which the readiness
  engine could later weight more heavily than a self-declared claim.
- Readiness score **history over time** (spec: "how readiness changed
  over time") — that needs a snapshot table storing computed scores with
  a timestamp, which fits naturally into Phase 6 (Progress Tracking).
- Anything from Opportunities, CollabVerse, Portfolio, etc. — those are
  Phases 3+.
